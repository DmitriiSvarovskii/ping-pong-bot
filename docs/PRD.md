# PingStats — Product Requirements Document

Статус: архитектурный baseline PS-001 и реализованные PS-002–PS-006: локальное
FastAPI-приложение, PostgreSQL infrastructure, users, development-аутентификация,
friendships и единое ядро матчей 1×1.

## 1. Видение и цели

PingStats — Telegram Mini App для учёта настольного тенниса: личных матчей, свободных игровых сессий и турниров. Продукт должен давать единый достоверный журнал результатов, рейтинг Glicko-2 и понятную статистику, оставаясь удобным для локальных компаний игроков.

Цели MVP:

- регистрация/обновление профиля Telegram-пользователя;
- друзья и приглашения;
- обычные матчи 1×1;
- свободные сессии с очередью «проигравший уступает место»;
- single-elimination турниры;
- рейтинг Glicko-2, история и базовая статистика;
- локальная разработка через безопасный `dev-login` до появления Telegram initData.

Не входят в PS-006: Telegram initData, Telegram Bot, game sessions, ratings,
tournaments, statistics, notifications, Docker/контейнеры, OAuth и парольная регистрация.

## 2. Роли

- **Игрок**: владелец профиля; участвует в матчах, сессиях и турнирах.
- **Организатор сессии**: создаёт сессию, формирует стартовую пару, завершает сессию.
- **Организатор турнира**: настраивает, допускает участников, запускает турнир и может записывать результаты.
- **Система**: валидирует счёт, определяет победителя, ведёт очередь/сетку, строит рейтинг и проекции статистики.

## 3. Пользовательские сценарии и правила

### 3.1 Пользователи и вход

При `/start` Telegram-профиль создаётся по уникальному `telegram_id` либо обновляется. Повторный запуск не создаёт дубль. Сохраняются UUID, Telegram ID, имя, фамилия, username, URL/идентификатор фото, даты регистрации и активности.

До этапа Telegram WebApp Authentication клиент вызывает `POST /api/v1/auth/dev-login`. Endpoint
доступен только при `APP_ENV=development`, не принимает Telegram ID или иной выбор пользователя,
атомарно создаёт либо находит обычного пользователя по настроенному фиксированному UUID и выдаёт
ограниченный по времени JWT. Все защищённые endpoints используют один контракт
`get_current_user`; смена auth-провайдера не меняет их и доменные сервисы.

Критерии приёмки:

- одинаковый Telegram ID всегда соответствует одному пользователю;
- профиль и `last_active_at` могут обновляться без смены UUID;
- production не раскрывает dev endpoint (404);
- токен просрочен — запрос отклонён; произвольная impersonation невозможна.

### 3.2 Друзья

Игрок отправляет заявку другому игроку, принимает, отклоняет или отменяет её; существующего друга можно удалить. Нельзя отправить заявку себе, повторную pending-заявку в любую сторону или заявку уже существующему другу. Принятие атомарно создаёт дружбу и завершает заявку. Повтор команды идемпотентен либо возвращает детерминированный conflict.

### 3.3 Единые правила матча

Матч всегда 1×1 и хранит снимок настроек: очки для победы в партии, минимальное преимущество, число выигранных партий для победы и рейтинговый признак. Победитель выводится сервером из партий; клиент его не задаёт.

Партия корректна, если:

- оба счёта — неотрицательные целые;
- победитель набрал не меньше `points_to_win`;
- разница не меньше `win_by`, а проигравший результат согласуется с игрой до преимущества;
- ничья невозможна.

Матч завершается, когда ровно один игрок первым достиг `sets_to_win`; после решающей партии дополнительные партии запрещены. Незавершённый набор партий нельзя записать как итоговый результат.

Обычный матч имеет `context=standalone` и проходит состояния
`pending → active → completed`. Приглашённый может принять (`active`) или отклонить
(`rejected`) приглашение. Создатель может отменить pending-матч; любой участник может
отменить active-матч, пока в нём не записаны партии. После `active` любой участник
записывает партии по одной или передаёт весь итог одним запросом. Сервер нумерует
партии, вычисляет победителя и завершает матч сразу после решающей партии. Повтор точно
того же полного результата идемпотентен.

В PS-006 `match_sets` хранит текущий итог. Исправление атомарно заменяет его и добавляет
неизменяемую запись `match_result_revisions` с автором, временем, полными JSONB-снимками
предыдущего и нового результата и необязательной причиной. Любой участник standalone-матча
может исправить результат в течение 24 часов после `completed_at`. Политики организаторов
сессий/турниров подключаются на их этапах. Каждая изменяющая команда блокирует матч;
для пошаговой записи и исправления клиент передаёт `expected_version`, а неактуальная версия даёт 409.

### 3.4 Свободная игровая сессия

Сессия содержит минимум двух уникальных участников, организатора, настройки матчей, стратегию ротации и текущую очередь. Жизненный цикл:

1. `draft`: организатор создаёт сессию и добавляет участников.
2. `active`: организатор выбирает первых двух; сервер фиксирует снимок очереди и создаёт матч №1.
3. Любой активный участник записывает результат текущего матча.
4. В одной транзакции сервер фиксирует результат, ротацию и создаёт следующий матч с очередным номером.
5. Цикл не ограничен по числу матчей.
6. Организатор завершает сессию (`completed`); новые матчи не создаются.

К активной сессии можно присоединиться: новый участник атомарно добавляется в конец waiting-очереди и это изменение фиксируется снимком. Участник из waiting-очереди может выйти сам; организатор может удалить его по тем же правилам. Игрок текущего матча сначала должен завершить либо отменить матч. Незавершённый сессионный матч отменяется без победителя, партий, рейтинга и статистики побед/поражений. После отмены сервер восстанавливает порядок до матча с учётом присоединившихся/вышедших ожидающих, сохраняет отдельный queue snapshot и не создаёт следующий матч до явного возобновления; после выхода/удаления сервер берёт первые два доступных места очереди. Каждая отмена и последующее изменение очереди аудируются.

Алгоритм `loser_rotates`:

- текущая пара удаляется с начала порядка игры;
- победитель остаётся первым;
- первый ожидающий становится вторым;
- проигравший добавляется в конец очереди ожидания;
- при двух участниках пара повторяется, а очередь ожидания пуста.

Незавершённый current match можно пропустить без результата, выбрав первого, второго либо обоих
игроков. Матч становится `cancelled` без winner/rating/win-loss. При пропуске одного второй остаётся
за столом, первый waiting становится его соперником, а пропущенный уходит в хвост. При пропуске
обоих waiting и прежняя пара объединяются в порядке `waiting → первый → второй`, после чего первые
двое образуют новую пару. Для двух игроков создаётся ровно один successor с теми же двумя разными
участниками; один запрос не запускает рекурсивную ротацию.

Каждому матчу `sequence_number` выдаёт сервер под блокировкой сессии; `(session_id, sequence_number)` уникален. Отменённый матч сохраняет номер, номера не переиспользуются. Время создания не используется как единственный порядок. Снимок очереди сохраняется после каждого изменения вместе с причиной и инициатором, поэтому ход сессии восстанавливается для расчёта серий побед, максимальных серий, серий внутри сессии, матчей подряд без ухода со стола и личных рекордов.

Страница сессии показывает локально отформатированный `completed_at` завершённых матчей и отдельный
лидерборд этой сессии. Для каждого исторического участника, включая вышедших и ещё не сыгравших,
он производно считает победы, поражения и мячи «за/против» только по валидным `completed` матчам
данной сессии. Cancelled/skip/active и standalone матчи не учитываются. Порядок: wins DESC,
point difference DESC, losses ASC, user UUID ASC; первые три места отмечаются медалями, по умолчанию
показываются первые пять.

Список «Мои игры» содержит только сессии, в которых пользователь когда-либо участвовал; публичного
каталога свободных сессий и режима open/closed в текущем контракте нет. Авторизованный клиент может
получить персональный realtime invalidation `sessions.updated` после create/join/leave и переходов
статуса. Событие не содержит идентификаторы сессий или персональные данные и означает только
необходимость повторить существующий REST-запрос списка. Посторонние пользователи его не получают.
На экране «Мои игры» обновление выполняется в фоне без reload, сброса текущей страницы и замены уже
загруженных карточек полноэкранным состоянием загрузки; при недоступном WebSocket используется
временный REST fallback.

Страница конкретной сессии автоматически обновляет состояние, участников, очередь, текущий матч,
историю и статистику после `session.updated` без reload и постоянного polling. Экран записи
результата сохраняет черновик при refetch того же матча, но не переносит его на другой матч или
версию. При HTTP 409 submit блокируется до получения актуального current match;
кешированное состояние остаётся доступным при временной фоновой ошибке.

Исправление старого результата:

- создаёт новую ревизию матча;
- уже сыгранные последующие матчи и снимки очереди не удаляются и не перенумеровываются;
- сессия получает состояние согласованности `needs_review`, если победитель изменился и фактическая последующая последовательность отличается от вычисляемой;
- оператор/будущий специальный workflow может подтвердить фактическую историю или создать компенсирующие действия; автоматического каскадного переписывания нет.

Критерии приёмки: последовательность непрерывна, два параллельных результата не создают два следующих матча, автор результата сохранён, любой момент очереди восстанавливается из истории; list invalidation публикуется только после commit и только историческим участникам.

### 3.5 Рейтинг Glicko-2

Начальное состояние: rating 1500, RD 350, volatility 0.06; `tau=0.5`. Все параметры конфигурируемы. В рейтинг попадает текущая ревизия каждого сыгранного завершённого рейтингового матча любого контекста. Нерейтинговые, отменённые матчи и walkover не влияют на рейтинг.

Рейтинговый период — календарные 24 часа `[00:00, 00:00)` UTC и закрывается ежедневно в 00:00 UTC. Результат и статистика побед/поражений сохраняются сразу, рейтинг публикуется только после закрытия периода. Для каждого игрока все результаты периода применяются одновременно по математически корректному Glicko-2; для неактивных игроков увеличивается RD, rating и volatility меняются согласно алгоритму. Вход периода хранит `match_id`, версию/отпечаток текущего результата и nullable-ссылку на последнее исправление, а также параметры алгоритма и версию реализации.

Локальный scheduler автоматически закрывает наступившие периоды. При старте приложения он находит и последовательно закрывает все пропущенные периоды, начиная с самого раннего; Celery и Redis не используются. Блокировка PostgreSQL, статус периода и версия расчёта не допускают параллельную публикацию. Повторный запуск идемпотентен. В development доступен ручной запуск того же `close_due_periods` use case. Исправление использованного результата делает затронутый период и все последующие `stale`; пересчёт выполняется с последнего корректного снимка, атомарно публикует новую версию и обновляет текущие рейтинги. Статистика побед не является частью rating aggregate.

### 3.6 Турниры

Турнир открытый либо закрытый с хешированным паролем, имеет лимит участников и снимок настроек матча. Для MVP формат — `single_elimination`.

Жизненный цикл:

1. `draft`: организатор редактирует настройки.
2. `registration`: игроки вступают; пароль проверяется, дубли и превышение лимита запрещены.
3. При наличии минимум двух участников организатор запускает турнир: состав блокируется, рейтинг каждого участника фиксируется, более высокий рейтинг получает более высокий seed. При равенстве используются меньший RD, затем UUID. Стандартное размещение single-elimination разводит сильнейших по секциям сетки; недостающие места заполняются BYE. В одной транзакции строятся раунды/узлы и матчи первого раунда.
4. В `in_progress` результат может записать участник конкретного матча или организатор.
5. Победитель занимает заранее определённый слот следующего узла; когда оба слота известны, создаётся общий матч.
6. Победитель финала становится чемпионом, турнир — `completed`.

До запуска участник может отказаться самостоятельно. После запуска самостоятельный выход запрещён; организатор оформляет техническое поражение (`walkover`). Walkover продвигает соперника без фиктивных партий и не включается в Glicko-2. Архитектура посева допускает будущие random/manual strategies, но MVP реализует только rating seeding.

Исправление результата после продвижения сохраняет ревизии и переводит турнир в `needs_review`, если затрагивает уже созданные/сыгранные downstream-узлы; сетка не переписывается молча.

### 3.7 Статистика, лидерборд, уведомления

Профиль показывает матчи, победы/поражения, win rate, партии, рейтинг и максимум, историю, личные встречи, серии, турниры и титулы. Источник истины — результаты и рейтинговые расчёты; быстрые таблицы статистики являются перестраиваемыми проекциями. Серии считаются по `completed_at`, а для сессии — по `sequence_number`.

Leaderboard сортируется по опубликованному текущему rating с оговорённым tie-breaker (RD, затем число рейтинговых матчей, затем UUID). MVP предусматривает уведомления: новая заявка в друзья, приглашение в матч/сессию/турнир, начало турнира и назначение следующего турнирного матча. Уведомления создаются после успешного commit через transactional outbox; отдельный модуль доставки не зависит от бизнес-сервисов, а aiogram является только адаптером. Полная реализация всех типов не требуется в ближайшей задаче.

Все перечисленные read endpoints требуют авторизации. Любой зарегистрированный пользователь видит список и профили игроков, rating, победы/поражения, завершённые обычные матчи и историю завершённых открытых турниров. Закрытый турнир и его матчи видны только организатору и участникам. Неавторизованный запрос получает 401. Видимость сессионных матчей ограничена участниками сессии и её организатором до отдельного решения о публикации.

## 4. Нефункциональные требования

- Корректность при конкурентных запросах и идемпотентность критичных команд.
- Аудит автора и времени результата/исправления/очереди/рейтинга.
- Версионируемый REST API `/api/v1`, единый формат ошибок и cursor pagination.
- Никаких секретов в репозитории; JWT secret только из окружения.
- До финального этапа локальное выполнение: uv, локальный PostgreSQL, Uvicorn и aiogram polling; без Docker, Docker Compose, Kubernetes и контейнерной инфраструктуры. Redis — только после отдельного согласования.
- Расширение новыми форматами турниров, стратегиями ротации и auth-провайдерами без изменения матчевого ядра.

## 5. Общие критерии MVP

- Все перечисленные сценарии покрыты API и автоматическими тестами.
- Инварианты дублирования и ссылочной целостности защищены БД.
- Любой завершённый матч имеет ровно двух игроков, итоговую ревизию и вычисленного победителя.
- История исправлений, рейтинга, сетки и очереди не теряется.
- Проверены конкурентные сценарии приглашений, записи результата, ротации и запуска турнира.
- Документация соответствует фактической реализации.

## 6. Отложенные, не блокирующие PS-002 решения

1. Считать ли walkover победой/поражением в общей статистике сыгранных матчей. До решения он хранится отдельным outcome и гарантированно не меняет Glicko-2 или статистику партий.
2. Публиковать ли историю свободных сессий зарегистрированным пользователям; пока она доступна только участникам и организатору.
3. Какие типы MVP-уведомлений разрешено отключать пользователю и нужен ли помимо in-app канал Telegram Bot.
