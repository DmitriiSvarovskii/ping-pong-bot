# PingStats — инструкции для разработки

## Статус и область проекта

PingStats — backend Telegram Mini App и Telegram-бота `@pingstatsbot`. Проект развивается как модульный монолит с элементами Clean Architecture. До финального этапа и отдельного письменного согласования используется только локальное окружение: запрещены Dockerfile, Docker Compose, Kubernetes и иная контейнерная инфраструктура, а также предложения установить Docker. Redis также запрещён без отдельного согласования.

Согласованные бизнес-правила описаны в `docs/PRD.md`, архитектура — в `docs/ARCHITECTURE.md`, схема данных — в `docs/DATABASE.md`, API — в `docs/API.md`, решения — в `docs/DECISIONS.md`. Нельзя менять их смысл без явного разрешения заказчика.

## Технологический стек

- Python 3.12+, FastAPI, Pydantic 2, pydantic-settings.
- PostgreSQL, SQLAlchemy 2 Async, asyncpg, Alembic.
- aiogram 3.
- pytest, pytest-asyncio, httpx.
- uv для зависимостей и запуска, Ruff для lint/format.
- Uvicorn для локального FastAPI; aiogram polling для локального Telegram Bot.

Не добавлять новый фреймворк, хранилище, брокер или инфраструктурный компонент без ADR и согласования.

## Архитектурные правила

- Сохранять границы модулей: `auth`, `users`, `friendships`, `matches`, `game_sessions`, `ratings`, `tournaments`, `statistics`, `leaderboard`, `notifications`.
- Зависимости направлены от delivery и infrastructure к application и domain. Domain не импортирует FastAPI, SQLAlchemy, aiogram или Pydantic transport-схемы.
- Общая проверка счёта и жизненный цикл результата принадлежат `matches`; сессии и турниры не дублируют эту логику.
- Application-сервисы координируют use case. Репозитории скрывают persistence. Одна команда использует один Unit of Work и одну транзакцию.
- Dependency Injection выполняется явно через FastAPI dependencies и фабрики приложения. Не использовать service locator и глобальные изменяемые singleton-объекты.
- Strategy применять только там, где есть реальная вариативность: рейтинг, формат турнира, ротация сессии, провайдер аутентификации.
- Делить код по бизнес-возможностям, а внутри модуля — на `domain`, `application`, `infrastructure`, `presentation`, если слой действительно нужен. Не создавать интерфейс с единственной реализацией без тестовой/архитектурной причины.
- Публичное взаимодействие модулей — через application API/порты и события после commit; не обращаться к чужим ORM-моделям из бизнес-сервисов.
- Даты всегда timezone-aware UTC. Внутренние ID — UUID. Telegram ID — BIGINT.
- Порядок матчей свободной сессии определяется только серверным `sequence_number`, уникальным внутри сессии; время создания не является источником порядка.
- Рейтинговый период — календарные 24 часа `[00:00, 00:00)` UTC. Glicko-2 использует конфигурируемые defaults: rating 1500, RD 350, volatility 0.06, tau 0.5.
- Исправления результата всегда добавляют ревизию. Участник может исправить свой матч 24 часа после завершения; организаторы сессии/турнира — соответствующие матчи без ограничения времени.
- Walkover является отдельным исходом без фиктивных партий и не является рейтинговой игрой.

## Правила PostgreSQL и миграций

- База данных является источником истины для инвариантов, которые можно выразить FK, UNIQUE, CHECK, NOT NULL и индексами.
- Конкурентные изменения агрегата защищать транзакцией и блокировкой `SELECT ... FOR UPDATE` либо optimistic version, как указано в `docs/DATABASE.md`.
- Не использовать floating point для рейтинга и вычислений, требующих воспроизводимости; применять `NUMERIC`.
- Автоматическое закрытие рейтинговых периодов реализовать локальным in-process scheduler и PostgreSQL-lock. Не добавлять Celery или Redis; после старта scheduler обязан последовательно обработать пропущенные UTC-периоды.
- Все изменения схемы выполняются отдельной Alembic-миграцией. Миграция должна иметь понятные `upgrade` и безопасный `downgrade`, если необратимость не зафиксирована явно.
- До создания миграции обновить проектную модель; после — сверить metadata и фактические constraints/indexes.
- Не редактировать уже применённые общие миграции. Не выполнять destructive/data-loss миграции без плана переноса и разрешения.
- Имена constraints и indexes должны быть стабильными и явными.

## Тестирование и качество

- Одна задача — один законченный результат без преждевременной реализации будущих этапов.
- Для domain/application логики обязательны unit-тесты; для репозиториев, транзакций, constraints и блокировок — integration-тесты с PostgreSQL; для API — HTTP-тесты.
- Проверять позитивные, граничные, запрещённые и конкурентные сценарии. Исправления ошибок сопровождаются regression-тестом.
- После каждой задачи запускать релевантные тесты, полный `pytest` при возможности, `ruff check .` и `ruff format --check .`.
- Не подменять незавершённую бизнес-логику заглушками. Разрешённое исключение — явно описанный `dev-login`.

## Документация и процесс

- Перед задачей проверить её зависимости и критерии готовности в `docs/tasks/README.md`.
- После изменения поведения синхронно обновить PRD/API/архитектуру/схему и при необходимости добавить ADR.
- Не реализовывать настоящую Telegram initData-аутентификацию до отдельной задачи. `dev-login` доступен только в development, не принимает пользовательские идентификаторы и в production не публикуется/возвращает 404.
- Все player/profile/history endpoints требуют авторизации. Закрытые турниры и их матчи видны только организатору и участникам.
- После каждой задачи дать отчёт: изменённые файлы, решения, выполненные проверки, ограничения и следующая задача.
- Не менять правила матчей, ротации, исправлений, рейтинговых периодов или турнирного продвижения без подтверждения заказчика.
